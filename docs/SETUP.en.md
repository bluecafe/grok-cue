# Deploying to a server

This guide puts grok-cue on a Linux server, has Cue send signed requests to it, and lets Grok Bot receive the forwarded notice. Every address, email, path, and key here is an example. Replace `hook.example.com` with your own domain. Strings starting with `replace-with-` are not secrets; replace them with values generated by the commands below.

A short overview and response codes are in [README.en.md](../README.en.md), body fields in [DESIGN.en.md](DESIGN.en.md), and the agent version of this procedure in [AI_SETUP.en.md](AI_SETUP.en.md).

Example values:

| Item | Example | Replace with |
| --- | --- | --- |
| Domain | `hook.example.com` | Your domain |
| Server IPv4 | `203.0.113.10` | Server's public IPv4 |
| Server IPv6 | `2001:db8::10` | Server's public IPv6; skip if none |
| Install folder | `/opt/grok-cue` | Any folder |
| Settings file | `/opt/grok-cue/.env` | `.env` in that folder |
| Listen address | `127.0.0.1:8160` | A port not exposed to the internet |
| Reply email | `cue@example.com` | The address to allow |

## 0. Prerequisites

Have the following ready before installing; check each with the command shown.

| Prerequisite | Check | Expected |
| --- | --- | --- |
| Git | `git --version` | A version is printed |
| Python 3.11 or newer (`requires-python = ">=3.11"` in `pyproject.toml`) | `python3 --version` | `Python 3.11` or newer |
| Caddy (server, for HTTPS) | `caddy version` | A version is printed |
| Service account `bridge` (server) | `id bridge` | `uid=…(bridge)` |

If the service account does not exist, create it on the server:

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin bridge
id bridge
```

## 1. Domain and DNS

1. Open the DNS settings where your domain is managed.
2. Add an A record named `hook` (full name `hook.example.com`) pointing to the server's public IPv4. `203.0.113.10` is a placeholder.
3. If the server has IPv6, add an AAAA record with the same name. `2001:db8::10` is a placeholder. Skip it if there is no IPv6.
4. Save. DNS may take a while to propagate.

Check:

```bash
dig +short hook.example.com A
dig +short hook.example.com AAAA
nslookup hook.example.com
```

The A result should show the server IPv4, and the AAAA result (if created) the server IPv6. If empty or different, recheck the record name and value.

## 2. Install and run on Linux

Python 3.11 or newer is required. Paths are examples.

```bash
sudo mkdir -p /opt/grok-cue
sudo chown "$USER" /opt/grok-cue
git clone <repository-url> /opt/grok-cue
cd /opt/grok-cue
python3 -m venv .venv
source .venv/bin/activate
pip install --require-hashes -r requirements.lock
cp .env.example .env
```

Open `.env` and fill in the values from section 4. Then restrict permissions:

```bash
chmod 600 /opt/grok-cue/.env
sudo chown bridge:bridge /opt/grok-cue/.env
stat -c '%U:%G %a' /opt/grok-cue/.env          # bridge:bridge 600
sudo -u bridge test -r /opt/grok-cue/.env && echo ok
```

`bridge` is the example user from the systemd unit's `User=`/`Group=` below. If you use another user, change both places.

```bash
pytest
```

If `pytest` passes, start the process. It listens only inside the server; the proxy in section 3 exposes it to the internet.

```bash
source /opt/grok-cue/.venv/bin/activate
cd /opt/grok-cue
uvicorn app.main:app --host 127.0.0.1 --port 8160
```

The app reads `.env` from the working directory. Without the `cd` it cannot find the settings file.

To keep it running after reboot, save this example systemd unit as `/etc/systemd/system/grok-cue.service`. The unit is a documentation example only; the repository does not ship a unit file. `bridge` is an example user; create it on the server and give it ownership of the install folder.

```ini
[Unit]
Description=Cue Grok Bridge
After=network.target

[Service]
Type=simple
User=bridge
Group=bridge
WorkingDirectory=/opt/grok-cue
EnvironmentFile=/opt/grok-cue/.env
ExecStart=/opt/grok-cue/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8160
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now grok-cue.service
sudo systemctl status grok-cue.service
```

After changing settings, reload with `sudo systemctl restart grok-cue.service`.

## 3. HTTPS reverse proxy

Example: Caddy receives `https://hook.example.com` and forwards to `127.0.0.1:8160`. Add this to the server's Caddyfile.

```caddyfile
hook.example.com {
    request_body {
        max_size 64KiB
    }
    reverse_proxy 127.0.0.1:8160
}
```

`request_body` `max_size` is an optional proxy-level copy of the app's 64 KiB limit. The app checks the size before authentication even without it.

After reloading Caddy, ports 80 and 443 must be open in the server firewall. Do not expose 8160. Once DNS points at the server, Caddy obtains a certificate.

Locally without a proxy, use `http://127.0.0.1:8160`.

## 4. Environment variables

All settings live in one `.env` file, which the check script also reads. The app reads the nine names in `app/settings.py`. `PUBLIC_BASE_URL` is read only by docs and the check script, never by the app.

Generate the token and the HMAC key separately (run twice, use different values):

```bash
openssl rand -hex 32
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

Both print 32 random bytes as hex; either works. Paste the output into `.env` without quotes. Never paste it into chat, email, or the repository.

Example `.env`:

```dotenv
CUE_BRIDGE_TOKEN=replace-with-bearer-token
CUE_BRIDGE_HMAC_KEY=replace-with-hmac-key
CUE_BRIDGE_TOKEN_SECONDARY=
CUE_BRIDGE_HMAC_KEY_SECONDARY=
REPLY_TO_ALLOWLIST=cue@example.com
REPLY_TO_DEFAULT=cue@example.com
GROK_WEBHOOK_URL=
GROK_WEBHOOK_KEY=
GROK_WEBHOOK_KEY_HEADER=
PUBLIC_BASE_URL=https://hook.example.com
```

| Variable | Required | Read by | Meaning | Example |
| --- | --- | --- | --- | --- |
| `CUE_BRIDGE_TOKEN` | yes | app | Value Cue puts in `Authorization: Bearer`. The process will not start if empty | `replace-with-bearer-token` |
| `CUE_BRIDGE_HMAC_KEY` | yes | app | HMAC-SHA256 key, different from the token. The process will not start if empty | `replace-with-hmac-key` |
| `CUE_BRIDGE_TOKEN_SECONDARY` | no | app | Second Bearer accepted during rotation. Empty: primary only | empty, or a new token |
| `CUE_BRIDGE_HMAC_KEY_SECONDARY` | no | app | Second HMAC key accepted during rotation. Empty: primary only | empty, or a new key |
| `REPLY_TO_ALLOWLIST` | optional in code, needed in practice | app | Comma-separated emails, case-insensitive. Empty rejects every request with `400` | `cue@example.com` |
| `REPLY_TO_DEFAULT` | optional in code, needed in practice | app | Used when `reply_to` is omitted or blank. Must be on the allowlist; otherwise `400` | `cue@example.com` |
| `GROK_WEBHOOK_URL` | no | app | Address the Grok Bot routine listens on. Empty: no forwarding | empty, or `https://grok.example/hook` |
| `GROK_WEBHOOK_KEY` | no | app | Key sent to that address. Both URL and key are needed to forward | empty, or a separate key |
| `GROK_WEBHOOK_KEY_HEADER` | no | app | Empty: `Authorization: Bearer <GROK_WEBHOOK_KEY>`. Set: the bare key in that header | empty, or `X-Grok-Key` |
| `PUBLIC_BASE_URL` | check script | docs only | Address the check script calls. The app ignores it. The script stops if empty | `https://hook.example.com` |

Empty optional values mean "off". With `GROK_WEBHOOK_URL` and `GROK_WEBHOOK_KEY` left empty as in the example, copying the file does not forward anything. No address is hard-coded.

## 5. Cue and Grok Bot

### Request Cue sends

Cue sends JSON to `POST https://hook.example.com/v1/cue/tasks` (locally `http://127.0.0.1:8160/v1/cue/tasks`).

Headers:

- `Authorization: Bearer <CUE_BRIDGE_TOKEN>`
- `X-Cue-Timestamp`: current Unix seconds, within 300 s of server time
- `X-Cue-Signature`: HMAC-SHA256 hex of `{timestamp}.{raw_body}` (case-insensitive). No `sha256=` prefix
- `Content-Type: application/json`

There is exactly one dot between the timestamp string and the body bytes. Re-serializing the JSON changes the bytes and breaks the signature, so keep the original bytes.

When retrying:

- Keep the body bytes and the `idempotency_key` inside them.
- Regenerate only `X-Cue-Timestamp` and `X-Cue-Signature`.
- Resending the same signature returns `401`.
- The same body with a fresh signature returns `202` with the original `handoff_id`. It is not forwarded again.
- A different body with the same `idempotency_key` returns `409`.

If `reply_to` is omitted, `REPLY_TO_DEFAULT` is used and must be in `REPLY_TO_ALLOWLIST`. Field names and lengths follow [DESIGN.en.md](DESIGN.en.md). Never include a `task_id` key.

### Cue-side setup (unverified)

> [!NOTE]
> **Unverified:** Cue's public site ([cue.im](https://cue.im/)) and app store listings do not document a way for a Cue agent to **automatically send an HTTP POST with Bearer and HMAC signature headers** to a user-chosen URL. What follows is not Cue's actual UI; it is the **generic requirement any sender must meet**.

The sender (a Cue agent, or another program Cue delegates to) must keep these three values secret:

| Value | grok-cue name | Use on the sender side |
| --- | --- | --- |
| Endpoint | `PUBLIC_BASE_URL` + `/v1/cue/tasks` | POST target, e.g. `https://hook.example.com/v1/cue/tasks` |
| Bearer token | `CUE_BRIDGE_TOKEN` | `Authorization: Bearer <token>` header |
| HMAC key | `CUE_BRIDGE_HMAC_KEY` | Used to compute `X-Cue-Signature`; never sent as a header |

For every request the sender must:

1. Build the JSON body bytes once and keep them.
2. Put the current Unix seconds in `X-Cue-Timestamp`.
3. Put the HMAC-SHA256 hex of `{timestamp}.{body bytes}` in `X-Cue-Signature`.
4. POST with `Authorization` and `Content-Type: application/json`.

[`scripts/check_bridge.py`](../scripts/check_bridge.py) is the **reference sender** that implements exactly these steps (section 6). If Cue cannot send such a request itself, it must be sent from another environment Cue can use, the same way the script does.

### Notice Grok Bot receives

When both `GROK_WEBHOOK_URL` and `GROK_WEBHOOK_KEY` are set, grok-cue POSTs JSON to that address after acceptance, with a 5 s timeout. A failure does not change the `202` already returned to Cue.

If `GROK_WEBHOOK_KEY_HEADER` is empty the header is `Authorization: Bearer <GROK_WEBHOOK_KEY>`; otherwise the bare key arrives in the named header, without a Bearer prefix.

Only these 8 keys are sent ([DESIGN.en.md spec](DESIGN.en.md#spec)):

`handoff_id`, `repo`, `github_ref`, `status`, `summary`, `links`, `next_owner`, `idempotency_key`

`schema_version`, `title`, `created_at`, `reply_to`, `requested_by` are not included. This process never sends mail.

`forwarded: true` in Cue's response means a forward was scheduled for this request, not that Grok Bot succeeded. It is `false` when the URL or key is missing, or for a replay of the same body. `executed` is always `false`.

## 6. Verifying

> [!WARNING]
> Use `--send` only **before** enabling forwarding. If `.env` has both `GROK_WEBHOOK_URL` and `GROK_WEBHOOK_KEY`, the test handoff is really forwarded to Grok Bot. The script prints `forwarding ENABLED` first in that case.

First set the token, HMAC key, `REPLY_TO_ALLOWLIST=cue@example.com`, and `REPLY_TO_DEFAULT=cue@example.com` in `.env` and restart the process. With an empty allowlist even signed requests return `400`.

The health check has no auth. Replace the host with your domain.

```bash
curl -sS -D - https://hook.example.com/healthz
```

`200` with body `ok` means the process is up.

### Check script `scripts/check_bridge.py`

Shipped in the repository; standard library only. It never loads `.env` into a shell. A tiny `KEY=VALUE` parser inside the script reads it, so characters such as `&`, `$`, `;` are never shell-interpreted and secrets do not linger in the shell environment.

- **Dry run by default.** It builds a signed test request and prints only a summary (target URL, test `handoff_id`, body size, whether forwarding is configured) and **sends nothing**. Token and signature are shown as `<hidden>`.
- **Only with `--send`** does it call the server: health `200`, unsigned POST `401`, first signed POST `202`, replay of the same body `202` (same `handoff_id`, `forwarded=false`), different body with the same key `409`.
- Test-only values: `title` is `[TEST] connectivity check`, `summary` is `connectivity test — not a real task`, and a fresh `handoff_id` and `idempotency_key` are generated on every run. Status values and fields follow the spec unchanged.

Run from the install folder. For local-only checks set `PUBLIC_BASE_URL=http://127.0.0.1:8160` in `.env`.

```bash
cd /opt/grok-cue
sudo -u bridge .venv/bin/python scripts/check_bridge.py            # dry run, sends nothing
sudo -u bridge .venv/bin/python scripts/check_bridge.py --send     # only before forwarding is enabled
```

Use `--env PATH` if `.env` lives elsewhere. Resending the exact same timestamp and signature differs from the script's replay: that returns `401`.

## 7. Troubleshooting

| Symptom | Meaning | Check |
| --- | --- | --- |
| `401` `unauthorized` | Bearer, HMAC, time, or signature reuse failed. Which one is not disclosed | Token and HMAC key match the server `.env`; `X-Cue-Timestamp` within 300 s; fix clock skew; no `sha256=`; if you resent a signature, regenerate timestamp and signature |
| `400` `reply_to_not_allowed` | Address not accepted. `allowed` is the server list; the rejected address is not echoed | Is `REPLY_TO_ALLOWLIST` empty, is `reply_to` on it, is `REPLY_TO_DEFAULT` empty or off-list? `mailto:` and multiple recipients are rejected. Restart after changes |
| `400` `invalid_request` | Body format; see `fields` | `Content-Type: application/json`, body ≤ 64 KiB, field names per [DESIGN.en.md](DESIGN.en.md) |
| `400` `task_id_not_allowed` | A `task_id` key somewhere in the body | Remove it; use `handoff_id` only |
| `409` `idempotency_conflict` | Different bytes with the same `idempotency_key` | Resend the original bytes. Reordered JSON keys count as a different body. The first acceptance stays |
| `202` but `forwarded` is `false` | No forward was scheduled for this request | Both `GROK_WEBHOOK_URL` and `GROK_WEBHOOK_KEY` set? Replays are also `false` |
| `202` but nothing at Grok Bot | Scheduled is not delivered; failures do not change Cue's `202` | URL is the routine's receiving address; key header name matches; 5 s timeout |
| `dig` returns nothing | DNS does not point here yet | Check A/AAAA name and value; wait, then rerun `dig` and `nslookup` |
| Certificate error in browser or curl | HTTPS certificate not obtained | DNS points here, 80/443 open, Caddyfile name is `hook.example.com`, Caddy running |
| Local `8160` works, domain does not | Proxy layer | `uvicorn` on `127.0.0.1:8160`, Caddy `reverse_proxy` to that address. Do not expose 8160 |
| Process exits immediately | Required setting empty or malformed | `CUE_BRIDGE_TOKEN` and `CUE_BRIDGE_HMAC_KEY` set; each allowlist entry and `REPLY_TO_DEFAULT` is a single email |

`422` is never returned; schema errors are `400`. Unhandled errors are `500` `{"error":"internal"}`.

## 8. Protecting keys

- Keep `CUE_BRIDGE_TOKEN`, `CUE_BRIDGE_HMAC_KEY`, `GROK_WEBHOOK_KEY`, and rotation keys only in the server's `.env`.
- `chmod 600` so only the owner can read it.
- Never paste values into the repository, chat, email, or issues. The `replace-with-` strings in `.env.example` are placeholders.
- Logs never contain tokens, HMAC keys, the Grok key, signatures, bodies, or summaries.
- To rotate, put new values in `CUE_BRIDGE_TOKEN_SECONDARY` and `CUE_BRIDGE_HMAC_KEY_SECONDARY` and restart. Both old and new values are accepted meanwhile. Each request still needs one accepted Bearer and one accepted HMAC key.
- Once Cue uses only the new values, move them to primary, clear secondary, and restart. Old values stop working.
- Bearer and HMAC are always both required; matching only one returns `401`.
