# Cue 검토: 비정상 처리 설계 v5

## 결론

`docs/ABNORMAL_HANDLING.md`의 **[현행 구현] / [제안·미구현] / [미검증 전제]** 구분은 코드와 대체로 일치합니다. 특히 “결정”과 “구현 완료”를 구분하고, Bridge의 `202`와 실제 Grok 수신을 구별한 점이 적절합니다. 다만 2.1절에서 **계정 수준 권한과 Cue 연결 자격증명의 실제 권한을 구분하도록 문서 보완을 요청합니다.** 같은 계정이라는 사실만으로 해당 Cue 실행이 설정 변경이나 머지까지 할 수 있다고 단정할 수는 없습니다.

검토 기준은 요청에 지정된 `main`의 `ed9b525eb7744791c4dc96b9ea06ab55fc1f224d`입니다. 검토 중 `main`이 해당 SHA와 일치하고 원 문서가 존재함을 확인했습니다.

## 구분 표기 검토

- **[현행 구현]** 표기는 요청 모델, 인증, 중복 처리, 전달 경로 및 테스트가 뒷받침하는 범위에서 대체로 정확합니다. 현재 상태값은 `in_progress`, `needs_input`, `completed`, `failed` 네 가지이고, 요청 모델은 미지정 필드를 거부합니다. 현재 HMAC은 타임스탬프와 원본 바디를 서명하며, 같은 서명 재사용을 거부합니다. 다만 재생 기록과 idempotency 기록은 현재 프로세스 메모리에만 남습니다.
- **[제안·미구현]** 및 **[결정]** 표기도 타당합니다. 소유자가 결정한 목표라도 구현이 별개임을 문서가 분명히 밝히고 있습니다. 특히 SQLite 아웃박스, 재시도, 취소 상태 처리, HMAC v2, 순번 필드는 현행 기능으로 설명하면 안 됩니다.
- **[미검증 전제]** 표기는 Cue의 자동 재시도·실패 알림·취소 감시 등 아직 확인되지 않은 동작에 적절합니다. 단건 전송 확인은 자동화된 재시도나 모든 실행 환경에서의 지원을 증명하지 않습니다.
- GitHub 브랜치 보호 관련 내용은 코드가 아니라 날짜가 붙은 설정 관측치입니다. 이번 검토에서 사용한 연결은 보호 설정 API 읽기와 검토 브랜치 생성 요청 모두 `403 Resource not accessible by integration`으로 거부되었습니다. 따라서 보호 설정은 문서의 시간표시된 관측치로만 취급하고 현재 설정의 지속적 보장으로 확대 해석하지 않습니다.

## Grok에 요청하는 문서 보완

2.1절에 “동일한 소유자 계정의 계정 수준 권한과 Cue가 사용하는 GitHub App/토큰/브라우저 세션의 권한은 별개이며, 실제 허용 작업은 실행 시 자격증명의 저장소 범위와 권한에 따라 달라진다”는 구분을 추가해 주세요. 이 요청은 문구와 검증 근거의 보완이지, 계정 설정이나 연결 권한을 넓히라는 요청이 아닙니다. 머지·설정 변경을 하지 않는 작업 경계는 권한이 더 넓은 환경에서도 그대로 유지해야 합니다.

## Cue 담당 질문

### 재시도 때 서명은 어떻게 하나요?

재시도가 실제로 수행된다면 **매번 새 타임스탬프와 새 HMAC 서명**을 만들어야 합니다. 요청 본문 바이트와 `idempotency_key`는 그대로 유지하고, 이전 서명은 재사용하지 않습니다. Bridge는 동일 서명 재사용을 거부하고, 동일 키에 다른 본문이 오면 충돌로 거부합니다. 다만 Cue의 자동 재시도 기능과 횟수·간격은 현재 검증된 기능이 아닙니다. 이번 handoff에서는 지정대로 서명 요청을 한 번만 보냅니다.

### 취소 요청을 받으면 어떻게 처리하나요?

Cue에는 실행 중인 작업을 자동 감시하는 heartbeat가 없으므로 취소 메일을 받기 전까지 취소를 알 수 없습니다. 메일을 받은 시점부터 추가 작업을 멈추도록 최선의 대응은 할 수 있지만, 이미 실행 중인 작업을 즉시 중단하거나 완료된 부수 효과를 되돌린다고 보장할 수는 없습니다. 현재 Bridge가 받는 보고 상태에는 `cancelled`가 없으므로, 취소 보고는 `status: "failed"`로 보내고 `summary` 첫 줄에 `[cancelled]`를 둡니다. 취소 처리 자체도 자동 감시 기능으로 검증된 것은 아닙니다.

### 필요한 GitHub 읽기 권한은 어디까지인가요?

최소 읽기 검증에는 저장소 **Metadata: read**, **Contents: read**(브랜치·커밋·파일 확인), **Issues: read**, **Pull requests: read**(Issue/PR 존재·상태 및 handoff 참조 확인)가 적절합니다. 공개 저장소는 일부 읽기가 인증 없이 가능하지만, 비공개 저장소라면 해당 저장소에 한정된 이 범위가 필요합니다. 브랜치 생성과 PR 작성은 별도로 **Contents: write**와 **Pull requests: write**가 필요합니다. Issue 댓글도 맡는 경우에만 **Issues: write**가 추가됩니다. 관리자 설정, 머지, 배포, Actions, 비밀값에 대한 읽기 권한은 필요하지 않습니다.

### 0.1.0에서 HMAC v2와 `attempt` / `report_seq`를 지원할 수 있나요? 일정은요?

현재는 지원하지 않습니다. 코드의 HMAC은 v1이고, `attempt`와 `report_seq`는 요청 스키마에 없으며 미지정 필드 거부 규칙에 따라 보내면 400으로 거부됩니다. Cue는 서명 기준(메서드·경로의 정규화 포함), 필드 타입·증가 규칙, 순서 충돌 처리, v1/v2 공존 기간이 양측에서 확정되고 Bridge도 이를 구현한 뒤 Cue 측 지원을 구현·검증할 수 있습니다. 문서의 0.1.0은 목표 버전에 대한 결정이지 배포 일정이 아니며, Cue가 현재 날짜나 릴리스 일정을 약속할 수는 없습니다.

### 브랜치 이름 규칙은 무엇인가요?

Cue 작업 브랜치는 `cue/<task-slug>` 형식, 소문자 kebab-case를 사용합니다. 이번 브랜치 `cue/review-abnormal-v5`가 이에 맞습니다. 이는 Cue가 따를 작업 규칙이며, GitHub 저장소의 기술적 강제 규칙으로 확인한 것은 아닙니다.
